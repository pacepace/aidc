# aidc — Requirements

**What this covers.** Authoritative requirements list for `aidc` (AI Dev Container). Each requirement has a stable ID, priority, and a source pointer. Design documents in `docs/design-NN-*.md` reference these IDs. Task shards (written later) cite them as well.

## ID conventions

| Prefix | Area |
|--------|------|
| `CTR-NN` | Container base, runtime, mounts, profiles |
| `GIT-NN` | Git isolation and asymmetry |
| `DKR-NN` | Docker-in-Docker |
| `NET-NN` | Network egress and proxy stack |
| `CLI-NN` | `aidc` command surface |
| `RMT-NN` | Remote control (retired — relocated to CTR/CLI; control plane is MCP) |
| `MCP-NN` | MCP control plane (external AI orchestration) |
| `SEC-NN` | Safety model, taint, threat mitigation |
| `CI-NN` | Continuous integration |
| `REL-NN` | Release engineering and distribution |
| `K8S-NN` | Kubernetes backend |
| `TRS-NN` | 3tears adoption (aidc 2.0: the MCP server on 3tears, local and mesh faces) |

## Priority

- **P0** — Required for v1. Project does not ship without this.
- **P1** — Required for production confidence but acceptable to ship a partial v1 without.
- **P2** — Future work; tracked here so design can leave hooks for it.

## Source pointers

- **brief** — the original project brief
- **plan-2026-05-21** — clarifying decisions captured in the planning conversation on this date

## CTR — Container base, runtime, mounts, profiles

| ID | Requirement | Priority | Source |
|----|-------------|----------|--------|
| CTR-01 | The dev container uses a version-tagged Ubuntu LTS base image (currently 26.04) in the `Dockerfile`. `:latest` is forbidden. Digest pinning + scheduled holdback (e.g., Renovate `minimumReleaseAge: 30 days`) is P2 future work. | P0 | brief §1, plan-2026-05-21 |
| CTR-02 | The dev container is configured via `devcontainer.json` using the standard Dev Containers spec. | P0 | brief §1 |
| CTR-03 | The dev container includes the `ghcr.io/devcontainers/features/docker-in-docker:1` feature for nested Docker. | P0 | brief §1 |
| CTR-04 | The dev container includes the `ghcr.io/devcontainers/features/git:1` feature for full local git capability. | P0 | brief §1 |
| CTR-05 | Language runtimes are selected via a `profile` setting: `python`, `node`, `go`, `rust`, or `multi`. | P0 | brief §1, plan-2026-05-21 |
| CTR-06 | The host repo is mounted into the container read-write at a well-known path (e.g., `/workspaces/<repo-name>`). | P0 | brief §1 |
| CTR-07 | The container MUST NOT mount the host SSH agent socket. | P0 | brief §1 |
| CTR-08 | The container MUST NOT mount any GitHub credentials, tokens, or config (`~/.gitconfig` with credentials, `~/.config/gh/`, etc.). | P0 | brief §1 |
| CTR-09 | The container MUST NOT mount `~/.docker/` or `/var/run/docker.sock`. | P0 | brief §1, §3 |
| CTR-10 | The dev container is fully ephemeral — every `aidc create` produces a fresh container; persistent state lives only in the host-mounted repo. | P0 | brief safety model |
| CTR-11 | The CLI and dev container support macOS (Docker Desktop), Linux (native Docker), and Windows via WSL2. | P0 | plan-2026-05-21 |
| CTR-12 | The dev container MUST run a long-lived tmux session (named `main`) that Claude Code runs inside, and which persists across client detach. (Relocated from RMT-01.) | P0 | brief §5 |
| CTR-13 | The dev container MUST own its Claude Code config directory (`CLAUDE_CONFIG_DIR=/home/vscode/.claude`, on the dev-home volume). The host's `~/.claude/.credentials.json` and `~/.claude.json` MUST NOT be bind-mounted: Claude Code replaces both by rename, so a single-file bind mount goes stale on one side and is unwritable on the other (anthropics/claude-code#18443). Auth is either `CLAUDE_CODE_OAUTH_TOKEN` from `aidc claude-token` (inference-only; no Remote Control) or a `/login` inside the session, which MUST persist across `aidc restart` / `aidc upgrade` and is discarded by `aidc kill`. `aidc create` MAY seed the container's `~/.claude.json` from the host's so first launch skips onboarding; the seed MUST drop the host account, API keys, MCP server definitions and every other project's state, keeping only this project's trust / onboarding / allowed-tools entry. Sharing the whole `~/.claude` directory is rejected: it would expose every project's memory and history to the sandbox, and `~/.claude.json` lives outside it. Per-project memory (`~/.claude/projects/<encoded>/`) and plugins stay bridged from the host as before. `settings.json` MUST NOT be bind-mounted either: it carries `hooks` the HOST's Claude Code runs, so a session that could write it could run a command on the host. It is copied in at create and installed on the session's first start (until 2026-09-22 it was mounted read-write). The status-line script `~/.claude/statusline-command.sh` MAY be bridged read-only when `settings.json` names it, and ONLY that file, as a regular non-symlinked file, since nothing the session could have written may choose a mount source (amended 2026-09-22, review rev-20260922T015403Z-28cf6fcf). | P0 | conversation-2026-09-11 |
| CTR-14 | A session's Claude scratchpad MUST survive moving between host and container. Claude Code keeps per-session working files at `/tmp/claude-<uid>/<encoded-repo>/<session-id>/{scratchpad,tasks}`, which on the container's writable layer are destroyed by `aidc upgrade` and `aidc kill` — so a session that moved kept its transcript (CTR-13) and lost its working files. `aidc create` MUST bind-mount the host's `/tmp/claude-<uid>/<encoded-repo>/` at the identical path inside, keyed on the same encoded repo path as the memory bridge, toggleable via `share_scratchpad` (default true). The mount MUST be the per-repo subdirectory only, never the whole `/tmp/claude-<uid>` root, which holds every other project's scratchpad — the same rejection CTR-13 makes for `~/.claude`. It MUST be suppressed when the host uid is not the container's: the host dirs are mode 0700, so such a mount lands unwritable and Claude cannot create a scratchpad at all. Durability beyond that is explicitly NOT required — `/tmp` is reboot-cleared on the host, so a bridged scratchpad lives exactly as long as a host session's, and `aidc kill` does not reap the host-side directories. Preparing those directories MUST NOT be able to fail a session: both levels sit under world-writable sticky `/tmp`, so a path already held by another user or by a symlink MUST be refused rather than followed, and every failure MUST cost only the bridge. KNOWN GAP: uid equality is a proxy for the real precondition (can the container write the host dir). On macOS, where Docker Desktop remaps bind-mount ownership, it suppresses the bridge on a platform CTR-11 supports; unverified on that platform. | P1 | conversation-2026-09-12 |

## GIT — Git isolation

| ID | Requirement | Priority | Source |
|----|-------------|----------|--------|
| GIT-01 | Inside the container, `git status`, `diff`, `add`, `commit`, `branch`, `checkout`, `rebase`, `stash`, `log`, `blame`, `show` MUST all work. | P0 | brief §2 |
| GIT-02 | Inside the container, `git push`, `pull`, `fetch`, and any remote-touching operation MUST fail. | P0 | brief §2 |
| GIT-03 | The GitHub CLI (`gh`) MUST NOT be installed in the container. Amended 2026-11-24 (owner rulings "The git container does not do prawduct's work", "Sessions make their own worktrees on Kubernetes"): `gh` in the container is aidc's stand-in (`.devcontainer/gh-standin.sh`), holding no login and reaching nothing itself; on Kubernetes it hands pull requests to the user's git container as request files. Amended 2026-11-24 (owner ruling "The git container works on Docker too"): on Docker too, in a session created after `aidc git setup`; without a git container it says none is set up and does nothing. | P0 | brief §2 |
| GIT-04 | Push prevention is achieved primarily by mount restrictions (no SSH keys, no credentials); see CTR-07, CTR-08. | P0 | brief §2 |
| GIT-05 | A system-level pre-push hook (`/etc/git-hooks/pre-push`) installed via `git config --system core.hooksPath` MUST hard-fail any push attempt as a belt-and-suspenders defense. | P1 | brief §2 |
| GIT-06 | The host machine retains full remote git capability (push/pull/fetch/gh) — the asymmetry is one-directional. | P0 | brief §2 |
| GIT-07 | GitHub issues go through the git container. `gitctl` gains issue verbs: list, view, create, edit (title, body, labels, assignees, milestone), comment, close and reopen. They act only on repos the user added, carry no AI attribution, and offer no delete, transfer or lock. The git agent uses them, and a session's `gh issue ...` (the aidc stand-in) hands them to the git container like pull requests, so a session's backlog work on GitHub issues works without a login in the session. Issue writes are decided by the request handler (gitreq), out of the agent's reach; they run at once in every mode, checked by gitreq, and never wait for approval (owner ruling 2026-11-26, Q-G1). | P0 | owner 2026-11-26 |

## NET — Network egress and proxy stack

| ID | Requirement | Priority | Source |
|----|-------------|----------|--------|
| NET-01 | All HTTP/HTTPS egress from the dev container MUST traverse the proxy stack; the container is configured with `HTTP_PROXY` and `HTTPS_PROXY` env vars pointing at the Squid sidecar. | P0 | brief §4, plan-2026-05-21 |
| NET-02 | The filtering model is **blocklist**, not allowlist. Default policy is permit; named threats are denied. | P0 | plan-2026-05-21 |
| NET-03 | DNS resolution from the dev container MUST use Quad9 (`9.9.9.9`, `149.112.112.112`) as upstream resolver. | P0 | plan-2026-05-21 |
| NET-04 | The Squid forward proxy MUST consult a file-backed blocklist refreshed from URLhaus data and HaGeZi Threat-Intelligence Feeds. **Amended 2026-10-22** (was: URLhaus, ThreatFox and HaGeZi, fetched from abuse.ch): abuse.ch now requires a per-user Auth-Key for every export and its URLs answer 410 Gone. By Pace's decision no Auth-Key is held: URLhaus data comes from the malware-filter project's keyless mirror (`malware-filter.gitlab.io`, falling back to `curbengh.github.io`), and ThreatFox, which has no keyless source, is no longer a feed. This moves trust for those entries to a single-maintainer mirror; the decision, its wording and the taint consequence are recorded in `.prawduct/change-log.md` (2026-10-22, malware feeds) and `docs/security-model.md`. | P0 | plan-2026-05-21 |
| NET-05 | A maintained state-actor TLD policy file MUST block requests to domains under configured TLDs (default: `.ru`, `.cn`, `.by`, `.ir`, `.kp`). | P0 | plan-2026-05-21 |
| NET-06 | A **refresher sidecar** MUST run alongside Squid in the proxy compose stack: fetch threat feeds on startup and every 6h thereafter, atomically write the blocklist (squid follows it without a reload: NET-16; until 2026-09-22 the refresher signalled squid to reload via a shared PID namespace). | P0 | plan-2026-05-21 |
| NET-07 | A **policy sidecar** MUST tail Squid's `access.log` in real time, detect malware-list hits, and write a taint flag to a shared volume location readable by `aidc status`. | P0 | plan-2026-05-21 |
| NET-08 | An **audit aggregator sidecar** MUST collect Squid access log, dev container shell history, and Claude Code session transcripts into a host-visible audit directory. | P0 | plan-2026-05-21 |
| NET-09 | Per-project blocklist additions in `<repo>/.aidc/blocklist.conf` MUST be merged with the global blocklist at proxy startup. Projects can only **add** blocks, never remove them. | P0 | plan-2026-05-21 |
| NET-10 | The proxy stack MUST live outside the dev container (separate Docker compose stack) so that processes inside the dev container cannot reconfigure or bypass it. | P0 | brief §4 |
| NET-10a | **Correction (2026-09-05).** NET-10 was only half-implemented until v1.3.0: the proxy stack did live outside the dev container, but nothing *forced* traffic through it. `HTTP_PROXY` is advisory — `env -u HTTP_PROXY curl https://example.com` returned 200 and produced no entry in `access.log`, so the blocklist did not apply and the policy sidecar could not taint on it. NET-14 supplies the missing half. | P0 | conversation-2026-09-05 |
| NET-11 | If the refresher cannot reach feed sources, the previous (last-good) blocklist MUST continue serving. Refresher failure MUST NOT block proxy operation. | P0 | plan-2026-05-21 |
| NET-12 | The refresher MUST fetch feeds from a hard-coded list of upstream URLs baked into the refresher image; it MUST NOT accept feed URLs from runtime configuration. | P1 | plan-2026-05-21 |
| NET-14 | The session bridge MUST be a Docker `internal` network by default, so no NAT exists for it and the dev container has NO route to the internet except through squid, which is dual-homed onto a separate egress network. Enforcement MUST NOT depend on anything inside the dev container: it is `--privileged` for DinD and can flush any rule it can see. Only `squid`, `refresher` (threat feeds), `policy` (taint webhook), and the single-purpose socat sidecars — port forwarders (CLI-13/14) and TCP egress relays (NET-15), each fixed to one target — may join the egress network; `dev` and `audit` MUST NOT. An `egress: direct` escape hatch MUST remain for sessions needing reachability an attached network cannot provide, and MUST say plainly that it disables enforcement. | P0 | conversation-2026-09-05 |
| NET-13 | A session MUST be able to attach its **dev container only** to named, existing Docker **bridge** networks, so it can reach another stack's services (database, queue, cache) by container name. The proxy sidecars MUST NOT be attached. `host`, `none`, and Docker's default `bridge` MUST be refused. Every attachment MUST pin gateway priority so that `aidc-<session>-net` remains the default route — otherwise an attached network silently captures all of the session's egress, squid-proxied traffic included. A session with no attachment MUST render a compose file identical to one produced before this requirement existed. | P1 | conversation-2026-09-05 |
| NET-15 | The operator MUST be able to name TCP destinations (`host:port`) a proxied session may reach — in their own config (`egress_tcp:`), with `aidc create --egress-tcp`, or live with `aidc egress <session> add` — without giving the session a route out. Each destination host MUST get one relay on the session network, reachable under the host's real name so TLS hostname checks still pass, forwarding only to that host's resolved address on the listed ports, and logging every connection to the session's audit dir. One relay per host, not per host:port: Docker answers a network alias with every container that carries it, so two relays sharing a hostname could hand a client the relay for the wrong port. The hostname MUST be resolved on the host (whose resolver can see overlay and split-horizon names) when the relay is created. Exception: a session created through aidc-mcp's `session_create` runs `aidc create` inside the aidc-mcp container, which cannot use the host's resolver, so its names are resolved there (the host's upstream DNS, without per-link resolvers); this is documented to operators, who can list an IP address instead. A destination that does not resolve, or that is the aidc-mcp address and port (MCP-12), MUST be refused. Relays MUST survive `aidc restart` and `aidc upgrade` (declared and live alike: they depend on neither the dev container nor its image) and MUST be removed by `aidc kill`. On Kubernetes a relay is its own pod, Service and NetworkPolicies, and the session resolves its name through its proxy pod's names responder (which answers nothing else), so live changes never restart the dev pod. | P1 | conversation-2026-09-21 |
| NET-16 | A new malware blocklist MUST take effect without squid dropping connections: squid never reloads for it (a squid reload is a restart and refused every connection for ~20 s with a multi-million-entry list; issue #34). Squid asks a lookup helper (its `external_acl_type` hook), which reads the byte-sorted list on disk and starts using a replacement the moment the refresher swaps it in. A listed domain MUST block its subdomains too, which is what the feeds intend and what the taint classifier already assumes. The helper MUST fail closed when it has no list to read. | P0 | conversation-2026-09-22 |

## MCP — Control plane (external AI orchestration)

| ID | Requirement | Priority | Source |
|----|-------------|----------|--------|
| MCP-01 | aidc MUST expose an MCP server (`aidc-mcp`) that AI orchestrators can connect to. | P0 | plan-2026-05-22 |
| MCP-02 | The server MUST be a single global instance per host (not per-session). It manages all sessions by name. **Amended 2026-11-25 for aidc 2.0 (K8S-07; Q-M4, a main-agent decision the owner may overrule):** on the Docker backend, one global instance per host as above; on the Kubernetes backend, one instance per user, in that user's namespace, managing that user's sessions by name. Both exist in 2.0; `aidc mcp` drives the one for the backend the config selects. | P0 | plan-2026-05-22; rulings-2026-11-23 (K8S-07), plan-aidc-2.0 §5 Q-M4 |
| MCP-03 | The server MUST run as a Docker container with lifecycle commands `aidc mcp start \| stop \| status \| logs \| token rotate`. **Amended 2026-11-25 for aidc 2.0 (K8S-07, TRS-23):** on Kubernetes the same verbs `aidc mcp start \| stop \| status \| logs \| token rotate` act on a single-replica Deployment in the user's namespace, with its state and access log on a persistent claim, run under the MCP ServiceAccount `aidc user add` makes (K8S-20). | P0 | plan-2026-05-22; rulings-2026-11-23 (K8S-07), plan-aidc-2.0 §5 Q-M4 |
| MCP-04 | Transport MUST be MCP streaming HTTP (not stdio, not SSE-only). | P0 | plan-2026-05-22 |
| MCP-05 | Authentication MUST use a single bearer token. Token is stored at `~/.config/aidc/mcp-token` with mode 0600. **Amended 2026-11-25 for aidc 2.0 (K8S-07):** on Kubernetes the token is a Secret in the user's namespace, never in the image or a ConfigMap; `aidc mcp` on the user's machines reads it with the user's own kubeconfig into `~/.config/aidc/mcp-token` (mode 0600) when they need it, so the orchestrator config is written the same way on both backends. | P0 | plan-2026-05-22; plan-aidc-2.0 §1 (MCP-05/06), W-M2 |
| MCP-06 | The server MUST auto-generate a token on first `aidc mcp start` if absent. `aidc mcp token rotate` MUST invalidate the prior token and restart the server. **Amended 2026-11-25 for aidc 2.0 (K8S-07, TRS-08):** on Kubernetes `aidc mcp start` creates the Secret when absent and `token rotate` replaces it and restarts the Deployment.
